# /fcode-review — 변경분 리뷰하고 고친다

**얇은 껍데기다.** 리뷰 방법론을 새로 만들지 않는다. 하는 일은 셋뿐이다: 범위를 정하고, 관점별로 병렬 리뷰를 띄우고, 고쳐도 안전한 걸 고친다.

## 먼저 — 내장으로 넘길 것

| 요청 | 넘길 곳 |
|---|---|
| 보안 점검 | `/security-review` |
| PR 에 코멘트 달기 | `/code-review --comment` |
| 레포 전체 감사 | 이 스킬 아님 |
| 빌드·테스트 실행 | `/full-loop` 의 검증 명령, 또는 `/verify` |

사용자가 이걸 요청하면 **그쪽을 안내하고 멈춘다.** 여기서 다시 만들지 마라.

## 1. 범위를 정한다

```
git status --porcelain
git diff HEAD
```

읽는 범위는 **세 겹**이다:

1. **diff** — 바뀐 줄
2. **변경된 파일 전체** — 바뀐 줄만 보면 맥락을 몰라 오판한다
3. **고친 함수의 호출자** — `grep` 으로 찾는다. 시그니처나 동작이 바뀌었으면 형제 호출자가 같이 깨진다

변경된 코드 파일이 없으면 그렇게 말하고 끝낸다.

## 2. 관점별로 병렬 리뷰한다

`Agent` 툴로 서브에이전트를 **한 메시지에 모아 띄운다**(그래야 동시에 돈다). 인자로 관점이 지정됐으면 그것만, 없으면 기본 셋 전부. **Stop 훅으로 자동 발화했을 때는 사용자에게 관점을 묻지 않는다** — 기본 셋 전부로 바로 돈다.

| 관점 | 보는 것 |
|---|---|
| **정확성** | 널 참조, 경계값, off-by-one, 삼킨 예외, 무한루프, 잘못된 조건, 리소스 누수 |
| **성능** | 핫패스 안의 할당, 불필요한 복사, O(n²), 반복 안의 I/O |
| **단순화** | 과설계 — 구현체 하나짜리 인터페이스, 산출물 하나짜리 팩토리, 안 쓰는 추상화, 이미 코드베이스에 있는 걸 다시 구현한 것 |
| **유니티** (`.cs` 있을 때만) | `Update`/`FixedUpdate` 안의 `GetComponent`·`FindObjectOfType`·`Camera.main`, 문자열 연결·LINQ·박싱 GC, `tag ==` 대신 `CompareTag`, non-alloc physics 미사용, 코루틴 누수, `Instantiate` 남발 |

각 에이전트에게 주는 것: goal(무엇을 하려던 변경인지), 범위 3겹, 그 관점 하나. **다른 관점은 보지 말라고 명시한다** — 안 그러면 넷이 같은 걸 네 번 보고한다.

각 에이전트가 돌려줄 것: `파일:줄` · 무엇이 문제인지 한 문장 · **재현/실패 시나리오** · 고치는 법 · **고쳐도 안전한가(safe_to_fix)**.

재현 시나리오를 못 쓰는 지적은 버려라. "이럴 수도 있다"는 지적이 아니라 소음이다.

## 3. 종합하고 고친다

1. **중복 제거.** 여러 관점이 같은 줄을 지적하면 하나로 합친다.
2. **고친다.** `safe_to_fix` 인 것만. 판단은 리뷰 결과가 한다 — 아래가 안전 기준이다:
   - **고쳐라**: 명백히 틀린 것, 동작을 바꾸지 않는 것, 되돌리기 쉬운 것
   - **고치지 마라**: 의도가 애매한 것, 공개 API 시그니처, 저장 포맷·직렬화, 남의 코드(`Packages/`, `Assets/Plugins/`, `node_modules/`, 벤더링된 SDK)
   - 애매하면 **안 고치고 보고한다.** 자동 발화하는 스킬이 자동으로 고치는 중이라는 걸 잊지 마라.
3. **고친 뒤 다시 확인한다.** 수정이 새 문제를 만들지 않았는지 그 파일을 다시 읽는다.

## 4. 보고하고 마킹한다

보고는 두 덩어리다:

- **고친 것** — `파일:줄` 과 무엇을 바꿨는지 한 줄씩
- **안 고친 것** — 지적과 왜 안 고쳤는지. 사용자가 판단할 재료다

보안 관련이 눈에 띄었으면 `/security-review` 를 한 줄로 안내한다. **직접 보지는 마라.**

마지막에 마킹한다:

```
"${CLAUDE_PROJECT_DIR}"/.claude/skills/fcode-review/stop-hook.sh --mark
```

이걸 빼먹으면 방금 한 수정이 새 변경분이 되어 **Stop 훅이 쿨다운이 풀리는 대로 다시 발화한다.**

## Stop 훅은 언제 발화하나

`stop-hook.sh` 는 게이트 4종을 **전부** 통과할 때만 턴을 막는다:

1. **세션 수정** — 이 세션이 Write/Edit 로 파일을 직접 고쳤다 (PostToolUse 훅 `stop-hook.sh --edited` 가 세우는 `.edited` 플래그). 외부에서 생긴 미커밋 변경에는 발화하지 않는다
2. **쿨다운** — 세션별 15분. 집중 작업 중에 매 턴 끼어들지 않는다
3. **해시** — 변경된 코드 파일 한정 해시가 마지막 마킹과 다르다. 코드와 무관한 파일(로그 등)이 생겨도 재발화하지 않는다
4. **임계값** — 변경된 코드 파일 ≥2개 또는 ≥5줄. 미달이면 마킹하지 않으므로 변경이 누적되면 발화한다

상태는 전부 TMPDIR(`fcode-review-state/<레포 키>/`)에 있다 — 재부팅하면 초기화되고, 그 대가로 프로젝트 트리를 안 건드린다.

## /full-loop 안에서

`/full-loop` 이 목표 충족을 판정하기 **직전에** 이 스킬을 부른다. 그때는:

- 사용자에게 묻지 않는다. 기본 관점 전부로 돈다
- 범위는 워킹트리 diff 가 아니라 **루프 브랜치의 커밋 전체**(`git diff main...HEAD`)로 잡는다 — 루프는 단위마다 커밋해서 워킹트리가 비어 있다
- 고칠 것은 고치고, **안 고친 심각한 지적이 남아 있으면 "미달"로 친다** — 루프가 다음 라운드에서 처리한다
- 마킹은 동일하게 한다

## 범위 밖

- **보안 리뷰** — `/security-review` 것이다
- **PR 코멘트** — 내장 `/code-review --comment` 것이다
- **테스트·빌드 실행** — `/full-loop` 의 검증 명령이 담당한다
- **리뷰 방법론 재발명** — 내장 `/code-review` 가 이미 한다. 여기가 보태는 건 자동 트리거, 유니티 관점, `/full-loop` 연동뿐이다
